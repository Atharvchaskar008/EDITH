## What this pack is

The team is building a system that predicts close approaches between satellites, ranks them by collision probability, and recommends avoidance burns. Atharv builds the main system, including every screen the user sees. This pack is an add-on that produces data the main system displays:

1. **Alerts.** When the picture changes between two runs, say what changed.
2. **Operator data.** A standard-format warning message and the data for a one-page briefing for each dangerous event.
3. **A prediction model** trained on real European Space Agency data: will this warning get worse or fade away?
4. **The pitch.** Slide text, demo script and answers to likely judge questions.

The pack is fully standalone. It must not import or assume any code outside its own folder. It works only with JSON files in the shapes below, and creates its own sample files to develop against.

## Task 2: alert engine

```text
Write compare.py.

compare_runs(previous: list[ConjunctionEvent], current: list[ConjunctionEvent], current_plans: list[ManeuverPlan], run_id: str) -> tuple[list[ConjunctionEvent], list[Alert]]

Matching rule: two events are the same if they have the same primary_id and secondary_id and their TCA differs by less than 10 minutes. Event ids may differ between runs because the TCA shifts; a matched event keeps the event_id and first_seen from the previous run.

For every matched event, append {run_id, pc_max, miss_distance_km} to its history, carrying the previous history forward. New events get first_seen = the run time and a one-entry history.

Alerts:
- NEW: an event not in the previous run with risk AMBER or RED. Severity WARNING for AMBER, CRITICAL for RED.
- ESCALATED: risk level went up. CRITICAL if it reached RED, else WARNING.
- DOWNGRADED: risk level went down. INFO.
- CLEARED: an event that was AMBER or RED in the previous run and is absent now. INFO.
- PLAN_READY: an event has a plan with decision MANEUVER and did not have one in the previous run (pass previous plans too if you need them; adjust the signature and tell me). CRITICAL.
An event already past its TCA at the run time is not reported as CLEARED.

Messages are single plain sentences a non-expert understands, for example:
"IRIDIUM 106 and COSMOS 2251 DEB: risk rose from AMBER to RED. Closest approach in 34 h at 0.41 km."
Use names when present, otherwise the catalogue numbers.

Command line: python compare.py <previous_run_folder> <current_run_folder> writes alerts.json into the current run folder and rewrites its events.json with updated history, first_seen and event_id. With only one argument (the first run ever), every AMBER or RED event is NEW.

Tests: one hand-written pair of event lists per alert kind; the TCA-shift case (matched at 9 minutes, not matched at 11); the ids-swapped case must NOT match (primary and secondary are not interchangeable); running the tool on the three sample runs produces the expected alerts, which you list in the test.
```

**Done when:** run it on sample runs 1→2 and 2→3. Run 2 must produce an ESCALATED, a NEW, a PLAN_READY and no CLEARED for the vanished GREEN event. Read the messages aloud; they should make sense to someone who knows nothing about satellites.

## Task 5: risk-trend model

```text
Build a model that predicts an event's FINAL risk from the warnings available at least 2 days before closest approach. Write train.py.

Data preparation:
- Target: the risk value in the last warning of each event.
- Use only events that have at least one warning 2 or more days before closest approach AND a last warning within 1 day of closest approach.
- Features, all computed only from warnings 2 or more days before closest approach (never from later ones, that would be cheating): latest risk, latest miss distance, latest relative speed, the latest position sigmas of both objects, time to closest approach of the latest warning, number of warnings so far, change in risk between the last two available warnings, mean and standard deviation of risk so far, second object's type as a category.
- Split train/test 80/20 BY EVENT so that no event appears in both. Fixed random seed.

Models:
- Baseline: predicted final risk = latest known risk.
- Gradient boosting (LightGBM, or scikit-learn HistGradientBoostingRegressor if LightGBM fails to install).

Report on the test set, for baseline and model side by side:
- mean absolute error and root mean squared error,
- for the question "does the event end with risk above -6?": precision, recall and F2 score, using the predicted value with a threshold you choose on the training set only.
Say plainly which one wins on each number. In the original competition the baseline was hard to beat, so if the model does not win, report that honestly and do not keep tuning past 20 minutes.

Outputs:
- ./out/risk_model_report.json with all numbers and the feature importances,
- ./out/risk_model.png: predicted against actual final risk on the test set, with both MAEs in the title,
- the saved model file in ./out/,
- predict.py with predict_final_risk(event: dict) -> float | None. Our own events only have: pc (convert to log10), miss_distance_km (convert to the dataset's unit), relative_speed_kms (convert), the sigmas, the time to closest approach, and the history list (use it for the count and the change in risk). Train a SECOND, smaller model on only the features we can supply, report its numbers separately, and use that one in predict.py. Return None if a needed input is missing. Document every unit conversion in a comment.

Tests: no test-set event id appears in the training set; predict_final_risk returns a float for a complete sample event and None when miss_distance_km is missing; the feature builder never uses a warning closer than 2 days.
```

**Done when:** the report shows baseline and model numbers side by side. Whichever wins, write the result in one honest sentence for the pitch.

Command line: python cdm_export.py <run_folder> writes one .cdm.txt file per RED or AMBER event into <run_folder>/cdm/.
